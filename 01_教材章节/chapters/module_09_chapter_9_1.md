# 第 9.1 章：模型调用不是魔法——最小可观察 LLM 客户端、消息合同与安全边界

**适用版本：** Python 3.11+  
**项目连接：** `projects/09-llm-contract-client/`（版本 0.1.0）

## 1. 本章目标

完成本章后，你能够解释语言模型调用的输入、输出与不确定性；能区分模型、系统指令、用户文本、token、传输层和应用业务规则；能用允许列表、字符/token 上限、固定任务、有限重试和最小日志实现一个可测试客户端；并能说明模型文字为什么既不等于事实，也不等于可执行命令、权限或 Agent。

## 2. 先纠正三个误解

“调用 LLM”通常被误解成：把问题交给一个知道答案的函数；让用户自己写 prompt；或把输出直接交给系统执行。三种理解都危险。模型调用是一项受成本、延迟、速率限制、概率输出、供应商失败、输入攻击和隐私约束影响的外部服务操作。应用必须先定义合同，才调用模型。

> **本章结论：** LLM 是产生候选文本或结构化候选数据的组件；它不是事实数据库、授权系统、代码执行器、工作流引擎或安全边界。

## 3. 从生产级 Agent 倒推

一个生产级 Agent 可能有模型、工具、记忆、状态、工作流、评测和人工介入。但第一步不是安装 Agent 框架，而是建立一个能回答以下问题的最小客户端：调用了哪个模型？任务输入边界是什么？结果是什么形状？失败是否可重试？成本/长度是否可观察？日志是否泄露正文？输出是否会产生副作用？项目 9 先实现这条窄边界，后续才把它接入检索和工具。

## 4. 一次最小调用的组成

```text
受控 PromptRequest
    │ task + text + request_id
    ▼
LlmClient
    │ 固定系统指令、模型允许列表、长度与重试策略
    ▼
LlmTransport Protocol
    │ 可注入；真实 SDK 或无网络假传输
    ▼
模型服务
    │ 生成候选文本与可选 usage
    ▼
CompletionResult
    │ 文本 + request_id + 尝试数 + 长度/token 摘要
    ▼
应用后续验证、展示或人工复核
```

每一层都有不同责任。把它们揉在 CLI、API 路径或全局变量中，会让测试和安全审计变得困难。

## 5. 模型 ID 不是用户输入

本次实时目录显示 `gpt-5-mini` 可用，并声明支持 JSON Schema、工具与视觉能力；它被项目选作**课程默认**，不是让任意请求传 `model`。[1] 项目构造器只接受：

```python
LlmClient(transport, model="gpt-5-mini")
```

并以 `allowed_models=frozenset({"gpt-5-mini"})` 固定允许列表。为什么？模型变更会影响成本、能力、上下文、日志、合规和测试基线。模型选择应是经审查的部署配置，不是普通用户输入字段。

## 6. 任务类型也必须受控

```python
class PromptTask(StrEnum):
    SUMMARIZE = "summarize"
```

当前项目只允许摘要。它不接受用户传入“任意系统提示”“任意角色”“任意工具定义”或“帮我执行以下命令”。固定任务使应用能为每种能力建立输入上限、输出 Schema、评测集、风险说明和权限策略。未来增加分类、提取或问答，应逐项扩展枚举、提示、测试和评测，而不是把 `task: str` 变成万能入口。

## 7. 系统指令、用户文本与数据边界

项目把经审查的系统指令与用户文本作为两个消息字段：

```python
messages = [
    {"role": "system", "content": fixed_system_prompt},
    {"role": "user", "content": user_text},
]
```

用户文本依然可能包含“忽略之前规则”“输出秘密”“执行工具”等内容；它是**数据**，不能替换应用的授权与控制代码。项目测试证明即使用户正文包含这类注入语句，固定任务与固定系统指令不变。模型可能仍生成不合适回答，因此提示不是安全边界，后续还需输入过滤、工具权限、输出验证和评测。[4]

## 8. 输入长度是资源和安全边界

项目默认最多接受 2,000 个字符，并拒绝空文本和未允许的控制字符。字符不是 token 的精确计数，但在进入远端服务前是简单、可预测的第一道资源上限。OpenAI 的安全建议也指出，限制用户可输入 prompt 的文本量有助于降低提示注入风险；限制输出 token 有助于降低滥用风险。[4]

长度限制不解决全部攻击：短句也能恶意，可信长文也可能必要。它需要与允许任务、可信来源、用户权限和后续领域验证一起使用。

## 9. token 是什么，为什么要看它

模型不是按汉字、单词或句子直接计费和限制，而按 token 的近似文本片段处理。不同模型和语言的 token 划分不同，因此项目不试图在本地猜精确成本；它只在供应商响应提供时记录 `input_tokens` 与 `output_tokens`。实时端到端验收返回了 token 摘要，说明“请求长度”和“模型计量”不是同一个概念。

> **实践规则：** 先设合理输出 token 上限，再根据真实 usage 与评测调整；不要让无限输出成为默认。

## 10. 输出 token 上限与文本上限是两层防线

项目向 GPT 系列传递 `max_completion_tokens=256`，并在本地把最终文本限制为 1,200 字符。前者约束远端生成预算，后者约束应用的展示、存储和下游处理预算。两层都需要：只依赖远端 token 上限不能处理意外长格式；只依赖本地截断可能已产生不必要成本或损失结构。

本课程的代理使用 Chat Completions，并要求 GPT-5 系列在需要 reasoning 时使用 `max_completion_tokens`；这与其他供应商家族参数不同。[1]

## 11. 为什么需要传输协议

```python
class LlmTransport(Protocol):
    def complete(...) -> TransportReply: ...
```

`Protocol` 描述“需要什么能力”，不绑定某个 SDK。`LlmClient` 依赖协议；`OpenAiChatTransport` 负责 OpenAI-compatible SDK；测试使用 `RecordingTransport`。于是 12 项核心测试无需网络、无需密钥、无需消耗模型调用，仍能验证重试、脱敏、输入/输出和错误合同。

这叫**依赖倒置**：高层业务规则不依赖具体供应商细节。

## 12. 真实 SDK 适配器应当做什么

`OpenAiChatTransport` 只做四件事：创建 SDK 客户端；构造固定的 Chat Completions 调用；把供应商 usage 提炼为最小 token 摘要；把供应商异常映射成短暂或永久失败。它不决定业务任务、不记录 prompt、不做无限重试、不执行输出，也不把原始响应对象泄露给上层。

把 SDK 细节关在一个文件内，未来更换供应商、模拟服务或升级 SDK 时，核心合同与测试影响更小。

## 13. 短暂失败与永久失败

| 失败类别 | 例子 | 项目行为 | 为什么 |
|---|---|---|---|
| 短暂失败 | 连接故障、超时、临时服务错误、临时限流。 | 有限重试。 | 稍后重试可能成功。 |
| 永久失败 | 认证、权限、未知模型、无效请求、非法 Schema。 | 立即受控拒绝。 | 重复发送不会修复配置/输入。 |
| 响应错误 | 空文本、超出本地长度。 | 本地受控失败。 | 传输成功不等于应用结果可用。 |
| 业务错误 | 输出不符合事实/领域规则。 | 由后续验证/评测处理。 | Schema/文本格式不能证明语义。 |

真实供应商错误分类会随 SDK 演进；适配器必须把分类测试为本项目稳定语义，而不是把供应商异常类型泄露到所有业务层。

## 14. 有限重试，而不是“出错就再试”

项目默认最多两次尝试，第一次短暂失败后等待 1 秒，再调用一次。重试日志只有任务、模型、尝试号、请求 ID 和等待时间：

```text
INFO llm_completion_retry task=summarize model=gpt-5-mini attempt=1 request_id=...
```

OpenAI 的速率限制文档说明，临时 `429` 可包含 `Retry-After`，SDK 会自动对合格错误重试；应用层加重试时应考虑 SDK 已做的重试，并限制次数和总时间。[3] 因而生产适配器需要避免“双重无限重试”，并在有有效 `Retry-After` 时优先遵守它。

## 15. 为什么失败请求也值得观察

速率限制按请求、token 等指标工作；失败请求同样可能消耗每分钟配额，持续重发不能解决限制。[3] 项目记录 `attempts`、输入/输出字符数和可选 token 摘要，能让运营者看到“请求是否太大”“重试是否过多”“模型是否返回异常长度”，而不记录正文。可观察性不是收集所有数据，而是记录支持决策的最少事实。

## 16. 最小日志与秘密边界

绝不记录以下内容：用户正文、固定系统提示、API key、完整供应商响应、原始异常文本、Authorization 头、完整工具参数。可记录：任务、模型、请求 ID、尝试次数、字符数、token 数、结果类别和延迟（后续补充）。

如果 API key 泄露或疑似被误用，应立即撤销并替换，而不是把它打印出来寻找来源。[4] 密钥只由环境变量或受控密钥管理系统注入；项目 CLI 不提供 `--api-key` 参数。

## 17. 请求 ID 与安全标识不同

请求 ID 关联一次调用和它的脱敏日志；幂等键关联同一业务接受重试；安全标识在适用时帮助供应商识别终端用户滥用模式。OpenAI 建议安全标识采用稳定且保护隐私的值，例如对用户名/邮箱进行哈希，而不是直接传递个人信息。[4] 项目 9.1 只实现请求 ID，不假装已经建立身份、安全标识或多租户权限系统。

## 18. 一次真实验收说明了什么

项目以 `course-llm-contract --text ... --verbose` 执行一次最小真实调用。结果显示固定模型 `gpt-5-mini`、任务 `summarize`、显式请求 ID、一次尝试、字符数与 token 摘要；日志未包含输入正文。它证明环境变量接线、SDK 适配器和输出边界可以工作。

它**不**证明模型永远准确、费用稳定、没有注入、所有语言都等质量、能够处理敏感内容、可在高并发下运行，或可作为 Agent 部署。单次成功是烟雾测试，不是评测报告。

## 19. 模型文本绝不能自动执行

以下代码无论模型多“聪明”都不可接受：

```python
subprocess.run(result.text, shell=True)
```

同样不能把 `result.text` 直接执行为 SQL、Python、文件路径、URL 请求或权限变更。模型输出必须先进入固定 Schema、允许列表、领域验证、权限检查和通常的人类批准。后续 Agent 章节会让模型提出**候选工具调用**，但代码仍是最终执行者。

## 20. 最小客户端当前不做什么

| 能力 | 当前项目提供 | 当前项目不提供 |
|---|---|---|
| 文字任务 | 固定摘要。 | 自由聊天、任意 prompt 模板。 |
| 模型 | 一个受审查模型。 | 自动模型路由、成本最优选择。 |
| 输出 | 受长度限制的文本。 | 严格 JSON Schema（第 9.2 章实现）。 |
| 重试 | 同步、有限、短暂失败。 | 流式、后台队列、无限重试。 |
| 安全 | 输入/输出上限、最小日志、无工具。 | 完整鉴权、审核、DLP、沙箱。 |
| 质量 | 单元合同和一次烟雾验收。 | 基准评测、事实核验、SLA。 |

明确“不做什么”可以防止读者把教学原型当作生产 Agent。

## 21. 如何从最小实现扩展

正确扩展顺序是：增加结构化输出 Schema 和本地验证；建立少量固定样例的评测集；为延迟、token、失败类别增加观察；再谨慎添加检索、工具和状态。错误顺序是：先给模型任意工具和 shell 权限，再补日志、限制和测试。复杂框架会放大未定义合同，不能替代它们。

## 22. 快速测试（5 题）

1. 为什么模型 ID 不能默认由用户请求决定？
2. 用户文本中出现“忽略系统提示”时，它在应用合同中应被视为什么？
3. 为什么远端 token 上限外还要有本地字符上限？
4. 哪些失败可以尝试有限重试，哪些不应重试？
5. 一次真实调用成功为何不能证明模型输出真实可靠？

**答案要点：** 1. 影响成本、能力、合规与评测基线；2. 不可信数据；3. 分别约束生成资源和应用处理资源；4. 短暂网络/服务/限流可有限重试，认证/请求/Schema 不应；5. 单例不代表事实性、鲁棒性、覆盖率或生产可靠性。

## 23. 代码阅读（2 题）

1. 阅读 `LlmClient.complete()`。指出验证、传输调用、短暂失败、永久失败、成功转换分别在哪里发生；为什么 `LlmTransport` 不应该记录日志正文？
2. 阅读 `OpenAiChatTransport.complete()`。它如何把 `APIConnectionError`、`RateLimitError` 和认证/请求类错误收敛为两种项目错误？若供应商 SDK 升级，你会把兼容修改放在哪里？

## 24. Debug（2 题）

1. 故意把 `allowed_models` 改为空或把默认模型改为未允许字符串，运行测试。解释为什么“模型不存在”应在发请求前失败。
2. 故意在 retry 日志中加入 `user_text` 或 `str(exc)`，运行脱敏测试。恢复代码，并列出为什么原始异常也可能泄露主机名、请求片段或密钥线索。

## 25. 编程练习（3 题）、逆向设计与课后项目

**编程练习：** 1. 增加受控 `classify` 任务，只允许固定标签集合，并为未知标签设计本地验证失败。2. 增加每个请求的最大 token 预算与每个会话的简单计数器，禁止以字符串估算替代供应商 usage。3. 为短暂失败增加带抖动的退避策略；测试它的最大尝试、最大累计等待与不重试永久失败。

**逆向设计：** 某 CLI 接收 `--model`、`--system-prompt`、`--api-key`、`--tool`，把用户全文、密钥和供应商异常写入日志，遇错无限重试，并把输出当 shell 命令执行。请从成本、秘密、提示注入、供应商变更、容量、重放、权限、测试、事实性、可观察性和 Agent 风险至少倒推十一项失败点，并逐项设计可自动验证的限制。

**课后项目：** 构建“课程摘要助手 v0.1”。要求：固定模型与任务允许列表；单独的传输 Protocol；输入/输出/token 上限；短暂/永久/响应/业务失败分类；有限重试；请求 ID；不记录正文、提示、密钥和异常细节；无网络假传输单元测试；一次明确标为烟雾测试的真实调用；README 写出模型目录时效性、不可执行输出和不等同事实的边界。下一章将输出从自由文本收紧为 JSON Schema。
