# 第 10.2 章：先证明“取到了什么”——RAG 检索评测、来源质量与安全反例

**适用版本：** Python 3.11+  
**项目连接：** `projects/10-rag-contract-workbench/`（v0.5.0：检索、来源约束回答与离线支持度评测阶段）  
**前置章节：** 第 10.1 章的受控语料、切块、来源、教学嵌入、内存索引与有限检索。

## 1. 本章目标

完成本章后，你能够把 RAG 的“检索得好不好”从模型回答里分离出来；能用固定公开夹具评测目标来源是否被召回、返回结果是否夹杂无关来源、每个块是否有完整来源，以及没有证据时是否安静返回空结果；能生成不记录查询或语料正文的可复现报告；也能把提示注入文档作为检索安全反例。

> **本章结论：** 在问“答案写得像不像”之前，先问“正确来源有没有被取到、取错了什么、是否保留了来源、没有证据时是否拒绝凑答案”。

## 2. 为什么普通单元测试不够

普通代码的输入与输出常是确定的：给定 `2 + 3`，应得到 `5`。检索系统却受切块、文本版本、特征提取、嵌入模型、索引、排序、过滤、阈值和 `top_k` 共同影响。即使程序没有异常，也可能漏掉正确块，或返回看似相关却无用的块。

OpenAI 的评测实践指出，生成式 AI 具有可变性，评测应尽早持续地建立，并将自动指标与人工判断结合；“看起来可用”不是可靠评测策略。[1] 本章的检索器暂不生成文本，仍需要评测，因为 RAG 的错误可以在生成前发生。

## 3. 检索评测与回答评测必须分层

| 层 | 核心问题 | 本章最小证据 | 不能证明 |
|---|---|---|---|
| 语料/切块 | 正确内容是否被收录为可追溯块。 | 稳定块 ID、范围、版本和指纹。 | 内容真实、最新或已授权。 |
| 检索 | 目标来源是否出现在有限候选中。 | 召回、精度、来源字段、空结果案例。 | 模型能正确解释片段。 |
| 生成 | 回答是否仅基于检索片段、引用准确且可读。 | 后续章节的回答/引用夹具与人工复核。 | 高风险事实或决策无须人工审查。 |
| 工具/行动 | 是否选对工具、参数和权限。 | 更后续模块的允许列表、审批和审计。 | RAG 本身授予执行权限。 |

如果检索失败，优化提示词或换一个聊天模型不会补回未取到的证据。反之，检索命中也不意味着模型会忠实引用。因此每层要各自测量。

## 4. 什么是静态评测夹具

静态夹具是版本化的、小规模、明确说明用途的输入与期望结果。项目的 `tests/fixtures/retrieval_evaluation.json` 只含自制公开课程文本与四个案例：函数来源、检索来源、注入文字作为数据，以及高阈值下的无证据。

夹具不是生产数据的缩影，更不是世界真相。它的价值是让任何人在无网络、无凭据、无费用的条件下，重复运行同一合同，并让改动产生可比较的结果。

## 5. 先定义目标来源，而不是先看分数

每个 `RetrievalEvaluationCase` 先写出 `expected_document_ids`。例如问题“函数 参数 返回值”期望来源是 `functions`，而不是“分数大于 0.7”。这是因为不同提供方、维度、切块和语言可能给出不同分数尺度；来源目标更接近我们真正想要验证的检索行为。

```python
RetrievalEvaluationCase(
    case_id="function-source-recall",
    query="函数 参数 返回值",
    expected_document_ids=("functions",),
    top_k=1,
    score_threshold=0.0,
    min_precision=1.0,
    tags=("happy-path", "source"),
)
```

查询正文只在内存中交给检索器。评测报告不持久化它，以避免把未来可能敏感的测试/生产查询泄露到报告中。

## 6. 召回：目标来源有没有出现

本项目按来源 ID 计算简化召回：

```text
matched_expected_count / expected_count
```

若期望来源有一个，且它出现在返回来源集合中，召回为 1.0；若没有出现，召回为 0.0。真实系统可按块、段落、证据句或人工相关性等级定义召回，但必须先写清单位。

OpenAI 文档中的文档问答案例使用 context recall 等维度来评估是否取得了回答所需上下文。[1] 该文档中的具体数值目标是一个示例，而非课程默认阈值或任何业务的通用 SLA。

## 7. 精度：返回的来源有多少是目标

简化精度是：

```text
matched_expected_count / returned_count
```

若只返回一个正确来源，精度为 1.0；若返回两个来源，其中一个正确，精度为 0.5。精度低会让后续生成层面对更多噪声、增加 token 成本，并可能让模型把无关片段拼进答案。

本项目在案例中用 `min_precision` 显式定义最低可接受值。它不是要追求数学上的完美，而是要让“多取了一堆不相关来源”成为可见失败，而不是被漂亮自然语言掩盖。

## 8. 来源完整性是独立质量门

即使目标 ID 命中，若没有块 ID、源版本或字符范围，调用者无法回到原文检查。本项目要求返回块至少具有 `document_id`、`chunk_id`、`source_version` 以及合法字符范围，才标记 `source_complete=True`。

OpenAI Retrieval 的示例响应包含文件来源、相似度、属性和片段内容。[2] 课程实现不依赖该 API，但采用同样的可追溯原则：回答层不能把“模型声称的出处”当成证据，必须保留实际检索块的来源链。

## 9. 空结果也是必须评测的行为

案例 `not-enough-evidence` 把查询阈值设为 1.0，并期望来源列表为空。在当前测试替身与公开语料下，它验证无关问题不会被硬塞进结果。通过条件是：返回数为零、召回和精度按空期望语义计算为 1.0，且来源完整性仍为真。

这不表示系统已经证明“火星问题没有答案”，只表示当前语料、索引、查询和阈值下没有足够候选。后续生成层必须把它转化为明确、可审计的“当前受控语料中未找到足够依据”，而不是自由编造。

## 10. 阈值是产品选择，不是神秘常数

`score_threshold` 决定哪些候选有资格留下。提高它通常减少噪声，却可能漏掉措辞不同的正确来源；降低它通常提高候选覆盖，却把更多无关块交给生成层。检索文档也说明可以使用分数阈值和混合排序调节返回相关性。[2]

| 改动 | 可能改善 | 可能伤害 | 应用的评测问题 |
|---|---|---|---|
| 提高阈值 | 减少低相关噪声。 | 目标来源被排除。 | 召回是否下降。 |
| 降低阈值 | 找到更多边缘相关块。 | 精度与成本下降。 | 误命中是否增多。 |
| 增大 `top_k` | 有更多证据供后续检查。 | 重复、噪声和上下文成本增加。 | 前 K 来源精度如何。 |
| 调整切块/嵌入 | 可能提升目标召回。 | 改变分数分布和回归行为。 | 固定夹具是否回归。 |

## 11. 不要用当前分数伪造可信度

某块得分 `0.81` 不表示“有 81% 概率为真”。它也不代表“81% 的用户会满意”，更不代表文档已授权。分数来自当前向量、距离算法和语料集合，是候选排序的内部信号。

报告保存精度与召回，而不是把单个分数写成“正确率”。后续若展示分数，也应说明其用途是调试或排序，并让用户可查看来源、版本和上下文。

## 12. 评测阈值必须随任务定义

不同任务的错误成本不同。面向内部课程笔记的低风险检索与面向医疗、法律、财务或生产操作的检索不能共享同一门槛。后者还需要领域专家审查、授权控制、来源新鲜度、冲突处理和明确的人工升级路径。

评测最佳实践建议把目标、数据集、指标、运行比较和持续评测明确下来，并用人工反馈校准自动评分。[1] 因此项目的 `4/4` 只说明四条教学夹具的当前状态，绝不升级为“安全”“准确”或“可上线”的宣言。

## 13. 夹具 Schema 是合同，不是随手 JSON

`RetrievalEvaluationCase` 验证案例 ID、查询长度、`top_k`、阈值、精度下限、目标来源重复与标签。无案例、重复 `case_id`、超预算值或空标签都会被 `EvaluationFixtureError` 拒绝。

这种验证的意义是：评测数据本身也会错。若夹具有重复案例、目标 ID 拼写错、门槛不合理或字段漏填，运行得出一个“通过率”并没有意义。夹具需要像代码一样审查、版本化和测试。

## 14. 评测要复用生产检索路径

最危险的评测写法是：另写一套“为了通过测试”的相似度函数，而生产系统使用另一套索引、排序或阈值。项目的 `evaluate_case()` 直接调用 `InMemoryVectorIndex.search()`，所以查询边界、向量维度、稳定排序、阈值和来源对象与 CLI 使用同一条路径。

```python
retrieval = index.search(
    case.query,
    top_k=case.top_k,
    score_threshold=case.score_threshold,
)
```

这不消除所有差异，但避免评测与生产合同从第一天就分叉。

## 15. 公开评测报告只保留最小证据

`RetrievalEvaluationReport.as_public_dict()` 只输出 suite 名称、案例计数、通过/失败计数，以及每例的 ID、标签、期望/命中/返回计数、召回、精度、来源完整性和通过状态。它故意不输出查询、块正文、标题、向量、系统提示、密钥或原始模型响应。

| 报告字段 | 为什么可保留 | 为什么不保留相邻正文 |
|---|---|---|
| 案例 ID / 标签 | 标识测试意图和失败类别。 | 不包含输入内容本身。 |
| 计数 / 指标 | 支持趋势和回归比较。 | 不能反推完整语料。 |
| 来源完整性布尔值 | 显示引用链是否存在。 | 不暴露标题、内容或路径。 |
| `passed` | 让 CI 判断门禁。 | 不等同于真实质量认证。 |

## 16. 为什么报告要原子写入

报告先写入同一目录的临时文件，再用 `Path.replace()` 替换目标路径。这样中途崩溃时，读者更可能看到旧完整报告或新完整报告，而不是半段 JSON。测试也检查不会遗留临时文件。

这是本地单文件的教学边界，不是跨机器事务、审计保全、备份、加密、并发锁或长期存储策略。报告仍应视为可能敏感的运行元数据，并按保留期和权限进行管理。

## 17. 提示注入案例为什么放进检索夹具

安全案例的文档文本包含“执行命令”，查询也会命中该块。评测通过并不是因为系统遵循了该句，而是因为它把该块**作为有来源的数据**返回。项目没有 shell、网络、文件写入或模型工具，因此文本没有可执行路径。

OpenAI 的安全指南建议对对抗输入进行 red-team 测试，并限制输入与输出；它也强调高风险场景中人工复核的重要性。[3] 提示注入资料说明第三方网页、邮件和文档内容可能试图诱导系统偏离用户目标。[4] RAG 评测必须把这类例子当成常规回归案例，而不是发布后才处理的事故。

## 18. 人工复核仍不可替代

自动化来源召回无法判断：文档是否过时；两个来源是否冲突；来源是否有权被当前用户看到；片段是否足以支持精确结论；回答是否误导；或风险是否需要升级。人应能打开真实来源、看到版本和上下文，并按职责做判断。

自动指标适合发现回归、比较切块策略和筛选候选；人工复核适合校准指标、处理高风险与发现指标盲区。不要把“人点了确认”简化为安全措施；复核者必须拥有理解和核验所需的来源信息。

## 19. 运行离线评测

```bash
cd /home/ubuntu/python_private_course/projects/10-rag-contract-workbench
.venv/bin/python examples/run_static_retrieval_evaluation.py
cat reports/module_10_static_retrieval_evaluation.json
```

脚本只读取课程自制公开夹具，用确定性测试嵌入构建内存索引，运行四例并写入可再生报告。它不读取 `OPENAI_API_KEY`、不访问网络、不调用聊天或嵌入服务。报告中的 `4/4` 是本地回归信号，不是供应商模型的测量结果。

## 20. 将评测接入质量门

目前 pytest 覆盖夹具全量通过、精度失败可见、重复案例拒绝、未建索引受控失败、报告脱敏和临时文件清理。CI 在 Python 3.11/3.12 上执行可编辑安装、pytest、mypy 与 Ruff。

后续每次改切块、向量提供方、排序、阈值、文档 Schema 或回答层，都应先运行静态检索评测，再增加来自人工复核的新案例。不要为了让旧夹具通过而删除困难、无证据或注入案例；那只会让数字变好、系统变盲。

## 21. 快速测试（5 题）

1. 为什么 RAG 要分别评测检索与生成？
2. 本章中的召回分子、分母各是什么？
3. 精度低对后续生成层会造成哪两类成本？
4. 为什么空结果案例可以通过，而不是算失败？
5. 注入文档案例的“通过”究竟证明了什么？

**答案要点：** 1. 两层失效机制不同；2. 命中的目标来源数与期望来源数；3. 噪声/误导风险与 token/延迟成本；4. 它验证系统没有无依据凑候选；5. 文本仍被作为带来源数据处理，未获得执行权限。

## 22. 代码阅读（2 题）

1. 阅读 `evaluate_case()`。说明当 `expected_document_ids=()` 且没有返回结果时，为什么召回和精度都定义为 1.0；再说明这一定义在什么产品场景下可能不够，需要额外的拒答质量判断。
2. 阅读 `write_public_report()` 和对应测试。列出写入前后的步骤、临时文件命名方式、哪些字段被排除；解释为什么“报告没有正文”不等于“报告完全没有隐私风险”。

## 23. Debug（2 题）

1. 把 `function-source-recall` 的期望来源从 `functions` 改成 `retrieval`。运行评测，观察是召回、精度还是两者失败；恢复夹具并说明为什么“调低 `min_precision`”不能修复错误目标。
2. 故意在 `as_public_dict()` 中加入 `query` 或 `chunk.text`。运行测试，确认脱敏断言失败；恢复实现，列出至少三种会因报告正文而被扩大暴露面的信息。

## 24. 编程练习（3 题）

1. 增加一组双来源案例，要求 `top_k=2` 且两个期望来源均出现。为重复来源、只命中一个来源、命中两个但多出噪声来源分别设计召回/精度预期。
2. 为案例增加 `expected_source_versions`，要求命中来源的版本也准确。写出“文档 ID 对但版本错”的失败测试，并说明版本正确仍不等于内容在事实层面可靠。
3. 新增一个 `report_schema_version` 和报告摘要比较函数。要求只比较允许的统计字段，不能读取查询/文本字段；为字段漏失、未知 schema 版本和报告原子替换失败写测试。

## 25. 逆向设计与课后项目

**逆向设计：** 某团队说：“我们有 95% 的 RAG 正确率。”进一步追问后发现：只人工挑了 20 个简单问题；没有固定语料版本；只看最终回答而不检查检索；没有目标来源、无证据和注入案例；把相似度当置信度；评测报告保存客户问题和原文；改切块后不重跑；没有人工复核；“95%”的计算单位也未说明。请倒推至少十项不能接受的主张或缺失控制，并为每项设计可复现指标、夹具、日志边界或人工流程。

**课后项目：** 将“课程检索器 v0.1”扩展为 **课程检索器 v0.2**。要求：版本化公开静态夹具；来源级召回、精度、来源完整性与空结果评测；至少一个注入文档反例；评测复用生产检索路径；报告原子写入且仅含 ID、标签、计数、指标和门结果；pytest 覆盖成功、指标失败、夹具错误、未建索引、报告隐私与临时文件；README、mypy、Ruff、CI；明确写出评测的样本范围与不能证明的事项。下一章才会讨论把有限来源片段交给模块 9 的受控模型合同，生成带引用的候选回答。
