# 第 12.1 章：框架不是权限——用图编排对照受限 Agent 合同

**适用版本：** Python 3.11+  
**前置章节：** 模块 11 的无框架有限状态、预算、审批、事件与离线评测。  
**本章边界：** 先理解框架抽象；不安装框架、不调用模型、不连接网络或真实工具。

## 1. 本章目标

本章比较无框架受限 Agent 与图编排框架的职责。读完后，你应能判断框架解决的是执行组织问题，哪些控制仍必须由应用自己实现。

## 2. 为什么现在才谈框架

若先学习 API，读者容易把状态、工具和审批交给黑盒。先手写最小合同后，才能看出框架只是把节点、边、状态和恢复组织得更方便。

## 3. 图编排是什么

图把节点视为受控步骤，把边视为允许迁移；状态在节点间传递。LangGraph 将自己定位为低层、有状态 Agent 编排运行时，可混合确定性与模型驱动步骤。[1]

## 4. 图不是业务规则

节点名称 `approve` 不能证明审批人真实存在，边 `send_email` 不能证明收件人、内容、权限或幂等性已经验证。业务合同必须写在节点外可测试的应用代码中。

## 5. 状态 Schema 仍由你定义

框架可以传递字典或类型化状态，但你仍要定义字段闭集、身份、版本、允许状态、计数器和敏感数据保留。不要把“状态可序列化”误当作“状态安全”。

## 6. 节点的正确职责

一个节点应做一件可说明的事：验证候选、请求审批、调用包装工具、记录最小事件或决定下一条允许边。混合模型、数据库、日志和副作用的巨型节点难以重放与审计。

## 7. 边的正确职责

边表达已验证的迁移条件，而不是让模型随意返回节点名。候选路由应被枚举、验证并映射到固定边；未知值默认拒绝。

## 8. 无框架状态机的映射

模块 11 的 `RUNNING → WAITING_FOR_APPROVAL → RUNNING/STOPPED` 可以映射为图节点和边，但 `AgentStatus`、`StopReason`、预算和参数验证仍是应用合同。

## 9. 工具调用仍需包装

框架提供 tool node 或集成不意味着应暴露任意 callable。每个工具仍应有名称允许列表、输入/输出 Schema、最小权限、超时、幂等与审计。

## 10. 模型输出仍是候选

图中的模型节点只能提出结构化候选。应用验证工具名、参数、资源范围、预算和审批后，才可把候选交给工具包装器。

## 11. 持久化解决什么

框架的 checkpoint 可保存线程范围状态，以支持恢复、人工介入与故障恢复；长期 store 则保存跨线程应用数据。[2]

## 12. 持久化不自动解决什么

持久化不自动提供加密、租户隔离、删除权、保留期限、迁移、冲突处理、幂等、成本控制或事实正确性。保存得更久可能扩大泄露面。

## 13. 线程 ID 是恢复指针

在图运行时中，`thread_id` 让恢复找到同一状态；复用它会继续已有 checkpoint，新 ID 会启动新的线程。[3] 因此它是受控标识，不应是任意用户文本或秘密。

## 14. 中断的正确含义

中断暂停执行并等待外部输入；它不等于“已经批准”。恢复值是新输入，必须经过身份、字段、权限、过期和业务规则验证。[3]

## 15. 重放风险

官方文档说明，恢复含中断的节点时，该节点会从开头重新运行。[3] 因此中断前的副作用可能被重复；设计应使此前代码纯净、可重放或幂等。

## 16. 审批点应该在哪里

审批应在将要发生受保护动作前，并展示经验证的最小摘要。不要在模型思考前、工具已经执行后，或含秘密/全文的界面中放一个笼统按钮。

## 17. 预算依旧在框架外

图可能循环、分支或重试。应用仍需步骤、工具调用、时间、并发和成本预算；每个预算耗尽都要有稳定停止原因和测试。

## 18. 追踪依旧要最小化

框架 trace 有助定位状态转换，但可能包含提示、状态或工具结果。必须定义采集字段、脱敏、访问控制、保留期限和删除流程，再启用生产追踪。[1]

## 19. 提示注入不会因换框架消失

不可信文档或用户文本仍可影响模型候选。结构化节点输出、字段闭集、工具审批和应用验证能减少流动，但不能让注入风险归零。[4]

## 20. 何时适合图框架

当长运行任务具有明确状态、暂停恢复、并行分支、可观察运行与大量受控节点时，图编排可降低重复样板。简单线性工作流不必为了“Agent”而引入框架。

## 21. 快速测试（5 题）

1. 图编排与业务权限的区别是什么？2. checkpoint 和长期 store 分别适合什么？3. 为什么恢复值仍要验证？4. 重放为何危险？5. 为什么节点名不是工具允许列表？

## 22. 代码阅读（2 题）

1. 将模块 11 的 `step()` 分成验证、预算、审批和工具四个假想节点。2. 阅读持久化表格，标出哪些字段不应进入跨线程 store。

## 23. Debug（2 题）

1. 设计一个中断前先发邮件的节点，说明恢复为何可能重复发送。2. 让路由候选为未知节点名，说明应在哪一层拒绝。

## 24. 编程练习（3 题）

1. 用纯 Python 构造节点/边枚举并拒绝未知边。2. 为 checkpoint 设计字段闭集和版本迁移失败测试。3. 为审批恢复值设计 `approved|rejected` Schema 与过期验证接口。

## 25. 逆向设计与课后项目

**逆向设计：** 某团队安装图框架后让模型返回任意节点名、将完整聊天写入持久化、在中断前转账、恢复时直接信任布尔值。倒推至少十项缺失的状态、权限、隐私、幂等和评测控制。

**课后项目：** 画出模块 11 Agent 的框架映射图，逐节点列出输入 Schema、输出 Schema、预算、停止原因、是否可重放、是否需要审批和不允许的副作用。只提交设计、测试与静态夹具，不提交真实工具。
