# 第 1.1 章：交互式解释器、脚本与第一个可复现程序

**示例：** `examples/module_01/repl_and_names.py`；**版本：** Python 3.11+。

## 1. 本章目标

你将区分交互式解释器与脚本，能在终端运行一个保存于文件的 Python 程序，并把一次实验转换为可重复的命令。

## 2. 为什么学习

交互式解释器适合快速验证一个想法，脚本适合保存、复现、测试和交付一个流程。二者共同构成开发的最小反馈循环。

## 3. Agent 中的作用

未来的 Agent 工具先以交互实验验证输入输出，再收敛为可测试脚本、服务或工作流。不能复现的实验不能成为可靠工具。

## 4. 前置知识

完成模块 0；能够使用 `pwd`、`ls` 与 `python3 文件名.py`。

## 5. 概念解释

交互模式在 `>>>` 提示符后立即执行一行输入；脚本是保存于 `.py` 文件的源代码。Python 官方教程说明示例中带 `>>>` 的行为输入，不带提示符的行为输出。[1]

## 6. 生活化比喻

交互模式像草稿纸，脚本像写入实验记录本的步骤。草稿帮助思考，记录本帮助别人复现。

## 7. 原理分析

`python3` 不带文件名时启动交互模式；带文件名时读取并执行脚本。脚本中的 `if __name__ == "__main__":` 让文件作为主程序运行时才执行入口函数。

## 8. 最小示例

```bash
python3
>>> 2 + 3
5
>>> exit()
python3 examples/module_01/repl_and_names.py
```

第二条命令会打印原任务与复制后更新的新任务。不要将 `>>>` 复制进脚本文件。

## 9. 逐行解释

| 部分 | 作用 |
|---|---|
| `build_task_preview` | 将标题、优先级与完成状态组织为一条任务预览。 |
| `main` | 提供本次可重复的输入。 |
| `print` | 将程序内部数据变成终端可观察输出。 |
| 主程序判断 | 防止测试导入模块时自动执行演示。 |

## 10. 常见错误

将 `>>>` 写进脚本会产生 `SyntaxError`；在错误目录运行会找不到文件；只在交互模式实验却不保存代码，会失去复现证据。

## 11. Traceback 分析

若运行 `python3 examples/module_01/repl-and-names.py`，报错提示找不到文件，说明解释器已启动但路径中的连字符与实际下划线不一致。先用 `ls examples/module_01`，不要改 Python 代码。

## 12. 错误案例

把所有代码粘贴进一次性交互会话，关闭终端后无法知道输入和修改历史。它可能曾经成功，却不是可交付程序。

## 13. 改进方案

每次实验后，把稳定步骤保存为命名脚本，写入运行命令、预期输出和一个测试。将“我刚才试过”改成“任何人可在项目根目录重跑”。

## 14. 工程实践

从第一行代码开始使用语义化文件名、模块说明、`main()` 入口和测试目录。任务管理器项目将一直沿用这套结构。

## 15. 性能优化

此阶段优化的是反馈速度：小脚本、短命令、明确输出和一次只验证一个想法，比提前堆砌复杂架构更快。

## 16. 安全问题

交互模式可以执行任意 Python；不要粘贴来源不明的代码，也不要在示例中硬编码密钥或个人数据。

## 17. 小项目

为任务管理器创建 `projects/01-task-manager/README.md`，写出用户目标、运行命令、一个任务样例和一项“不自动执行”的危险操作。

## 18. 单元测试

运行：

```bash
python3 -m unittest tests/module_01/test_repl_and_names.py -v
```

测试确认更新标题时返回新字典，原任务不被意外修改。

## 25. 逆向设计与课后项目

**逆向设计：** 假设一个初学者项目在 **交互式解释器、脚本与可复现程序** 上失败：输入不可复现、状态不清、错误无法定位、数据被静默覆盖或结果难以验证。倒推至少五项缺失的规则、测试、日志、命名或操作边界，并按“先阻止什么风险”排序。

**课后项目：** 在本章已有示例基础上完成一个小型、可运行、可测试的改造。项目必须写明目标、输入、输出、失败案例、运行命令、两个自动化测试和一个逆向设计结论；不得读取真实秘密、执行未经授权的网络/文件副作用，或把用户正文写入日志。
