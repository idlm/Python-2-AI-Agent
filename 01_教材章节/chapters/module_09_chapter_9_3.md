# 第 9.3 章：不要用一次成功代替质量——离线评测、提示注入与人工复核

**适用版本：** Python 3.11+  
**项目连接：** `projects/09-llm-contract-client/`（版本 0.3.0）
  
**前置章节：** 第 9.1 章的最小可观察客户端，以及第 9.2 章的严格结构化摘要与本地验证。

## 1. 本章目标

完成本章后，你能够区分单元测试、烟雾测试和模型质量评测；能设计少量可复现的静态夹具；能把结构有效性、关键词、预期复核信号、尝试次数和 token 预算组合成可解释的质量门；能理解提示注入为何是数据与权限问题；还能说明人工复核何时不可省略。

> **本章结论：** 一个模型调用“没有报错”只说明某条链路在某次输入上运行过；可靠性必须通过明确案例、可复现规则、失败证据和人工责任逐步建立。

## 2. 三种检查不能混为一谈

项目 9 故意把三种活动分开。单元测试验证代码合同；烟雾测试验证当前环境的接线；评测则验证在一组定义好的案例上，输出是否满足可声明的质量门。把它们混为“测试通过”会夸大系统能力。

| 活动 | 主要问题 | 输入来源 | 是否调用真实模型 | 本项目的结论边界 |
|---|---|---|---|---|
| 单元测试 | 代码是否按合同处理边界？ | 假传输与静态对象。 | 否。 | 证明本地逻辑可重复。 |
| 烟雾测试 | 凭据、SDK、代理和请求形状是否接通？ | 一条最小课程文本。 | 是，且仅一次。 | 不证明质量、事实性或容量。 |
| 静态评测 | 已定义案例是否通过明确质量门？ | 课程自制公开夹具。 | 否。 | 只说明这些案例与规则的结果。 |
| 生产监控 | 真实流量是否出现异常模式？ | 经治理的运行元数据。 | 可能。 | 需要隐私、权限、告警和运营设计。 |

## 3. 为什么从离线静态夹具开始

刚学习模型时，读者常想“多调用几次看看”。这会产生不可控成本、时间变化和难以复现的结果，还可能把私密输入写入记录。项目先用公开、静态、课程自制夹具，让质量规则与失败行为可以在断网环境中反复运行。

夹具不是世界的缩影。四条案例只覆盖：基础概念、信息不足、包含提示注入语句的文本、资源边界。它们的价值是建立**评测机制**，不是宣布模型已安全或准确地理解了所有中文材料。

## 4. 夹具的两半：规格与候选

`tests/fixtures/evaluation_cases.json` 定义每个案例的输入、期望关键词、预期不确定性、尝试上限、输出 token 预算和标签。`evaluation_candidates.json` 则给出一个固定的假模型结构化候选及其 token 计数。两份文件以 `case_id` 一一对应。

| 夹具部分 | 保存什么 | 不用于什么 |
|---|---|---|
| 案例规格 | 课程输入、质量门、标签。 | 生产用户数据或真实对话日志。 |
| 候选输出 | 假传输回放的 JSON 对象和 token 摘要。 | 宣称模型在任何时间都会产生相同结果。 |
| 公开报告 | ID、标签、通过/失败、关键词计数/覆盖率和元数据。 | 复述输入、摘要、关键点、关键词字面量、系统提示或完整 JSON。 |

评测代码在内存读取夹具，但持久化报告从设计上不包含正文。这使“可追溯”不等于“收集一切”。

## 5. 案例从风险倒推，而非从漂亮样本开始

只有“函数是什么”的正常样本，很容易让系统看起来很好。项目还加入“信息不足”案例，要求高不确定性；加入提示注入文本，要求候选明确把内容当数据、不执行其中指令；加入资源案例，检查字符、token 和本地验证这些边界词。

这是一种**逆向评测**：先问系统在哪些地方会被误用、误解或绕过，再为这些风险写可观察的最小案例。OpenAI 的安全建议强调应进行红队测试，并在高风险场景采用人工复核。[1]

## 6. 评测先复用本地 Schema 验证

夹具候选不是直接做关键词搜索。`run_static_evaluation()` 先把候选 JSON 交给 `_ReplayStructuredTransport`，再调用真正的 `StructuredSummaryClient`。这意味着空关键点、未知枚举、额外字段和非法 JSON 会在与生产结构化路径相同的本地验证中失败。

```python
client = StructuredSummaryClient(
    _ReplayStructuredTransport(candidate),
    max_attempts=1,
    max_output_tokens=case.max_output_tokens,
)
return client.summarize(case.input_text, request_id=f"evaluation-{case.case_id}")
```

因此评测不是另写一套“宽松解析器”。同一输出合同只有一套核心验证，降低了测试通过而生产拒绝的风险。

## 7. 第一条质量门：结构有效性

`schema_valid=True` 的前提不是“JSON 看起来正常”，而是结果已经通过第 9.2 章的顶层对象、字段闭集、字符串、数组、长度和枚举检查。若结构无效，评测立即抛出 `StructuredOutputError`，不会把它包装成一个“低分但成功”的案例。

这样做能让故障清楚地归属为合同失败，而不是把模型格式错误混入关键词分数。它同样提醒我们：结构有效只是质量门的入口，而不是最终质量。

## 8. 第二条质量门：关键词覆盖

项目将 `summary` 与 `key_points` 合并成可搜索文本，然后判断期望关键词是否出现。内存中的质量门计算匹配数、缺失数与覆盖率；公开报告只保存这些数值，不保存关键词字面量，从而不会因为未来夹具关键词变化而扩大报告内容。

```python
searchable = " ".join((summary.summary, *summary.key_points)).casefold()
matched_count = sum(
    keyword.casefold() in searchable for keyword in case.expected_keywords
)
missing_count = len(case.expected_keywords) - matched_count
keyword_coverage = matched_count / len(case.expected_keywords)
```

关键词是低成本、可重复的启发式规则，不是语义理解证明。模型可以堆砌关键词却误解概念，也可以正确转述但没有使用预期措辞。后续更严格的任务可加入人工标注、来源核验和单独的评审程序。

## 9. 第三条质量门：不确定性与人工复核

信息不足案例的期望值是 `high`。这不意味着程序可以因 `high` 自动拒绝用户，也不意味着 `low` 就应自动执行；它只是测试模型候选是否正确表达“材料不足、需要人工补充”的受控信号。

| `uncertainty` | 课程中的解释 | 合理的下游候选动作 | 不应推导的结论 |
|---|---|---|---|
| `low` | 结果表达的犹豫程度较低。 | 正常展示，仍保留反馈入口。 | 内容已被验证为真。 |
| `medium` | 文本可能含歧义或风险提示。 | 标记给人工或要求补充上下文。 | 系统已完成安全判断。 |
| `high` | 结果明确表明信息不足或不确定。 | 人工复核、补充资料或拒绝自动化下游。 | 模型精确计算了错误概率。 |

人工复核的职责是结合来源、上下文、权限和后果做判断，而不是机械确认模型的句子。

## 10. 第四条质量门：尝试次数与 token 预算

评测报告还判断 `attempts <= max_attempts` 与 `output_tokens <= max_output_tokens`。这是因为一个“文本漂亮但反复重试、过度输出”的系统仍可能在成本、延迟和容量上失败。模型使用量并非只影响账单；它也影响速率限制、用户等待和服务稳定性。[2]

本夹具把 token 数作为固定的假传输元数据，绝不伪称为真实模型成本测量。真实调用只能在供应商返回 usage 时记录摘要，并要以实时模型目录为准。

## 11. 公开报告为什么不保存正文

`write_public_report()` 写入的字段包括案例 ID、标签、关键词匹配/缺失**计数**、覆盖率、质量门布尔值和聚合计数。它故意不含 `input_text`、`summary`、`key_points`、关键词字面量、系统提示、候选 JSON 或完整异常。写入采用临时文件后原子替换，避免半写入报告被误读为完整结果。

```python
payload = json.dumps(report.as_public_dict(), ensure_ascii=False, indent=2, sort_keys=True)
with NamedTemporaryFile(..., delete=False) as temporary:
    temporary.write(f"{payload}\n")
    temporary_path = Path(temporary.name)
temporary_path.replace(path)
```

“报告不含正文”的测试不是形式主义：它把最小化日志原则变成可回归验证的工程合同。

## 12. 当前离线报告读法

运行以下命令会生成 `reports/module_09_static_evaluation.json`：

```bash
.venv/bin/python examples/run_static_evaluation.py
```

当前四条课程案例全部通过。这个数字应读作“4 个固定候选通过了 4 条固定规则”，而不是“模型准确率 100%”。报告不包含假候选正文，所以可由案例 ID 和门的结果追溯，而无需复制输入内容。

## 13. 提示注入到底是什么

提示注入是指不可信内容试图改变模型的行为边界，例如要求“忽略之前规则”“泄露系统提示”“执行命令”或把自己伪装成高优先级指令。问题不在于一句文本是否带有某个关键词，而在于应用有没有把不可信内容与授权、工具和数据边界混在一起。

项目的注入案例不是让模型“破解”攻击，而是检查课程摘要合同能否表达基础原则：用户文本是数据，模型和应用不执行其中命令。官方建议通过限制输入、限制输出、红队测试与人工审查减轻提示注入和滥用风险。[1]

## 14. 系统提示不是权限系统

即使系统消息写着“不要执行命令”，模型仍可能被复杂上下文影响，也可能生成不合适内容。因此系统提示是行为引导，不是访问控制列表，更不是代码级授权。真正的权限边界应在模型外实现：固定任务、模型允许列表、输入限制、Schema、参数验证、服务端身份、工具允许列表和人类批准。

> **安全规则：** 不可信文本可以进入模型作为数据；它不得直接改变程序能够调用什么、读取什么、写入什么或向谁发起请求。

## 15. 输入限制是缓解，不是检测器

项目默认限制输入字符，拒绝未允许控制字符；这降低了资源消耗和一些滥用表面积。它无法证明短文本无害：一句“删除全部数据”很短，但在错误的工具链中仍危险。相反，长的可信资料可能是合法需求。

因此输入长度限制应与数据来源、用户权限、任务允许列表和输出/工具边界共同使用。它不是“发现注入”的分类器，也不应成为拒绝正常用户的唯一依据。

## 16. 输出限制也是安全边界

远端的 `max_completion_tokens` 限制生成预算，本地的字段长度和数组数量限制下游负载。两者共同避免模型返回超长段落、巨大数组或为下游展示/存储制造意外压力。安全建议同样指出限制用户输入和输出 token 可降低滥用与注入风险。[1]

不过，限制长度并不能让一条错误短语变真，也不能让一条格式正确的 URL 安全。下游仍需依据操作类型做域名、路径、SQL 参数、文件权限和身份验证等确定性检查。

## 17. 日志、评测与隐私的三个层次

| 位置 | 可记录的最小信息 | 禁止记录 | 目的 |
|---|---|---|---|
| 运行日志 | 模型、请求 ID、尝试、字符/token 数、结果类别。 | 输入、系统提示、密钥、完整 JSON、原始异常。 | 诊断容量和稳定性。 |
| 离线报告 | 案例 ID、标签、关键词计数/覆盖率、门结果、聚合数。 | 夹具正文、候选正文、关键词字面量、提示和完整响应。 | 可重复质量门。 |
| 人工复核材料 | 经授权、最小必要的上下文与来源。 | 超出职责的秘密、无关个人数据。 | 对高后果结果作责任判断。 |

同一段文本在不同层的保存必要性不同。最小化原则不是“永不记录”，而是只为已定义目的记录最少必要数据，并让访问、保留和删除受到治理。

## 18. 红队案例如何逐步增加

增加案例时不要一口气复制大量网络攻击语料。先为每一类风险写一个清晰、公开、非敏感的最小句子，并明确预期结果。例如：要求改变规则、要求泄露秘密、伪造工具成功、包含不可信网页摘录、包含矛盾事实。每次增加案例都应说明它测试的是输入边界、输出合同、人工复核信号，还是未来工具权限。

案例应版本化、可复现、可撤回。若必须使用真实用户材料，必须先有明确授权、脱敏、访问控制、保留期和审查程序；本教材项目不把真实用户内容放入仓库。

## 19. 失败不是“调大 temperature”的信号

当案例失败时，第一步应定位失败门：是 JSON 无效？字段超界？关键词缺失？不确定性不符？重试过多？还是 token 超标？不同失败需要不同改进：修代码、修 Schema、补充输入、调整任务定义、增加人工复核，或明确拒绝自动化。

直接反复调模型参数或把失败样例排除，会制造“只对漂亮样本有效”的错觉。任何提示或模型改变都应重新运行全部固定夹具，并新增能够捕获此前故障的案例。

## 20. 评测不能替代事实核验

关键词覆盖、Schema 和不确定性都是代理指标。它们不能验证一条法律是否现行、一个医学建议是否安全、一个财务数字是否准确，或一份来源是否可信。事实性需要可追溯来源、时间戳、领域规则和适当的人工专业判断。

项目 9 因此只做课程摘要，不接入外部搜索、检索、数据库或工具。第 10 模块会先建立受控检索合同与检索评测，之后才讨论让模型利用外部资料的方式。

## 21. 快速测试（5 题）

1. 单元测试、烟雾测试和静态评测各自回答什么问题？
2. 为什么离线评测报告不能包含夹具输入和候选摘要？
3. `schema_valid=True` 为何仍不足以说明质量高？
4. 提示注入案例通过后，为什么仍不能给模型工具权限？
5. 一个案例的 token 预算超标但关键词全命中时，为什么应视为失败？

**答案要点：** 1. 分别验证代码合同、环境接线和固定案例质量门；2. 因为正文可能含敏感内容，报告只需保存可追溯元数据；3. 它只表示形状与本地边界有效；4. 提示不是权限边界，工具还需要代码级授权与参数验证；5. 成本、延迟与容量也是合同的一部分。

3. 为评测运行添加一个版本字段和夹具文件的 SHA-256 摘要。报告可用于比较两次运行是否使用同一套夹具，但不得包含原文或把哈希当作访问控制机制。

## 25. 逆向设计与课后项目

**逆向设计：** 某团队展示了一次模型调用，得到格式正确的 JSON，随后宣称“准确、安全、可自动化”。他们把真实用户 prompt、系统提示和完整答案上传到评测平台；只保留全部通过的案例；没有注入样例；`low` 不确定性会触发自动数据库写入；输出 token 无上限；失败时无限重试；日志记录原始异常；工具参数不经代码验证。请从样本偏差、隐私、成本、重试、提示注入、授权、事实性、输出执行、可复现性、审计、人工复核、报告解释、供应商变更和 Agent 风险至少倒推十四项问题，并为每项写出一个可验证的控制措施。
