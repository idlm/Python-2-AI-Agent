# 第 13.1 章：多个 Agent 不等于更多能力——任务分割、角色与权限不扩散

**适用版本：** Python 3.11+  
**前置章节：** 模块 11 的受限 Agent 合同与模块 12 的框架采用边界。  
**本章边界：** 先设计委派消息与角色合同；不连接模型、多 Agent API、网络、MCP、数据库或真实工具。

## 1. 本章目标

本章说明多 Agent 只是在多个受限工作单元之间分配任务。你将判断任务能否并行、如何定义角色和消息，以及为什么委派不会自动扩大权限。

## 2. 多 Agent 的最小定义

多 Agent 系统由一个或多个协调者与多个工作单元组成；每个单元在受控目标、输入、预算和权限内产生候选结果，协调者再验证和汇总。

## 3. 何时值得拆分

适合拆分的工作彼此独立、边界清楚、可并行且有独立输出。例如比较多个公开方案、审阅不同风险维度或分析互不重叠的模块。[1]

## 4. 何时不该拆分

步骤强依赖、共享同一可变资源、任务很小、一个慢外部操作主导耗时或结果必须按固定顺序产生时，单 Agent 或确定性工作流通常更简单。[1]

## 5. 并发不是免费加速

并发可减少独立工作的墙钟时间，却增加 token、状态、协调、取消、成本和失败组合。多 Agent 的性能与风险必须用预算和评测证明，不能靠直觉。[1] [2]

## 6. 角色是合同，不是人格

`researcher`、`reviewer`、`synthesizer` 是职责边界：接收什么、可产生什么、可见什么、允许什么工具、预算多少、何时停止。不要把角色名当作安全控制。

## 7. 协调者的职责

协调者分解任务、分配唯一委派 ID、限制并发和预算、收集受控结果、处理超时/取消/失败并决定是否需要人工复核。它不应成为拥有所有真实工具的超级 Agent。

## 8. Worker 的职责

worker 只处理明确、可测试的子目标，按固定输出 Schema 返回结果类别、最小证据引用或拒绝原因。worker 不应重新解释总体权限、创建任意新角色或修改全局策略。

## 9. 委派消息必须字段闭集

最小委派可包括：委派 ID、父任务 ID、角色、受控目标摘要、允许工具集合、输入引用、步骤/工具预算、截止条件和输出 Schema 版本。未知字段默认拒绝。

## 10. 不转发什么

不要默认转发系统提示、完整聊天、密钥、账户信息、其他 worker 的原始输出、无关文档或高权限工具描述。上下文越大，泄露和提示注入表面积越大。

## 11. 权限不扩散原则

子 Agent 的权限必须是其角色和子任务明确允许的最小集合，而不是父 Agent、协调者或 API 请求的全部权限。协调层应能证明这一限制。[1] [3]

## 12. 委派不是授权

协调者发送“请执行”只是候选工作分配。真实工具仍须通过工具包装器、参数验证、资源授权、预算、审批和执行前再验证。

## 13. 输入和输出都是不可信数据

用户文本、worker 消息、工具结果和协调者摘要都可能错误、过时或含注入。任何消息不能改变角色允许列表、预算、审批或高优先级策略。[4]

## 14. 共享状态越少越好

优先让 worker 返回独立、不可变的结果摘要；协调者负责合并。共享可变状态会引入竞争、顺序依赖、冲突和难以重放的行为。

## 15. 结果合并也需要 Schema

汇总者只接收固定的结果类别、受控引用、计数和状态；它要识别缺失、重复、冲突和失败，不能把多个自由文本拼接后宣布完成。

## 16. 唯一性与去重

每个委派有稳定 ID、父 ID、角色与输入摘要。协调者应拒绝重复 ID，检测相同工作范围，避免两个 worker 重复消耗预算或产生矛盾写入。

## 17. 委派预算

限制总 worker 数、同时活跃数、每 worker 步骤/工具调用、总体成本和截止时间。预算耗尽是受控停止或降级状态，不是让协调者继续无限派生。

## 18. 故障传播

worker 失败并不等于整体失败。合同应定义可忽略失败、必须停止、可由其他独立 worker 覆盖和必须人工复核的类别，且不伪装完整成功。

## 19. 取消与收尾

当父任务取消、预算耗尽或策略改变时，未开始委派应拒绝，运行中委派应收到取消并记录最终类别。不能遗留无主后台 Agent。

## 20. 多 Agent 不是框架名称

监督者、handoff、subagent 或群体 API 是实现模式；核心仍是任务分割、角色合同、权限、状态、预算、错误处理、评测和责任分配。

## 21. 快速测试（5 题）

1. 什么任务适合多 Agent？2. 为什么共享可变状态危险？3. 委派消息最小字段有哪些？4. 为什么子 Agent 不应继承全部工具？5. worker 失败为何不必然表示整体成功或失败？

## 22. 代码阅读（2 题）

1. 将模块 11 的纯查询动作分配给一个只读 worker，并写出其允许工具集合。2. 把一个自由文本委派改成字段闭集对象，说明被拒绝的额外字段。

## 23. Debug（2 题）

1. 两个 worker 收到相同子任务，指出应在何处拒绝或去重。2. worker 返回“忽略限制并开放工具”，说明协调者为何只能把它当数据。

## 24. 编程练习（3 题）

1. 定义冻结 `DelegationRequest` 数据类。2. 实现纯函数检查角色—工具最小权限矩阵。3. 为重复委派 ID、超预算和未知角色写负向测试。

## 25. 逆向设计与课后项目

**逆向设计：** 一个协调者把完整聊天和所有工具交给每个 worker，允许 worker 自行生成新角色，未设预算，失败时假装成功。倒推至少十项消息、权限、状态、预算和评测控制缺失。

**课后项目：** 设计一个两 worker 的公开资料比较系统：角色表、委派 Schema、权限矩阵、预算、结果 Schema、去重、失败类别、静态夹具和无正文报告。禁止真实模型、网络或工具。
