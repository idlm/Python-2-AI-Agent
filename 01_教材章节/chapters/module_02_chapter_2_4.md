# 第 2.4 章：Lambda 与类型注解——让函数接口更清楚

## 1. 本章目标
理解 Lambda 的适用边界，并用类型注解表达函数预期输入输出。

## 2. 为什么学习
可读接口降低协作和调试成本；简短匿名函数不应替代清晰命名。

## 3. Agent 中的作用
工具参数和结构化输出需要明确类型；模糊接口会扩大模型调用失败面。

## 4. 前置知识
完成第 2.1–2.3 章。

## 5. 概念解释
Lambda 是单表达式匿名函数；类型注解使用 `name: type` 与 `-> type` 说明意图，运行时默认不自动验证。

## 6. 生活化比喻
类型注解像包裹标签，说明应该装什么；标签不会替你检查包裹内容。

## 7. 原理分析
命名函数适合复杂和复用逻辑；Lambda 适合非常短的局部转换。注解帮助读者、编辑器与类型检查器理解契约。

## 8. 最小示例
```python
def is_high_priority(priority: int) -> bool:
    return priority == 1
labels = ["a", "bb"]
lengths = list(map(lambda text: len(text), labels))
```

## 9. 逐行解释
注解表示参数期望整数、返回布尔；Lambda 接收一项文本并返回长度。

## 10. 常见错误
不要用长 Lambda 隐藏业务规则；不要以为注解会阻止错误输入。

## 11. Traceback 分析
将字符串与数字错误比较或计算时仍可能发生异常；注解只帮助更早发现问题。

## 12. 错误案例
把复杂权限判断压成一行 Lambda，代码审查无法识别默认拒绝是否生效。

## 13. 改进方案
复杂规则使用有名称函数、文档和测试；在外部输入边界加实际验证。

## 14. 工程实践
公共函数必须有类型注解；返回结构稳定；为工具参数建立可机器读取的 Schema 留出接口。

## 15. 性能优化
选择表达清晰的形式；Lambda 不天然更快。

## 16. 安全问题
注解不是安全验证；权限和工具参数必须由运行时规则验证。

## 17. 小项目
为文本分析函数添加 `str`、`int`、`dict[str, int]` 注解，并用命名函数实现排序规则。

## 18. 单元测试
测试正确类型、边界值和错误类型输入的处理策略。
