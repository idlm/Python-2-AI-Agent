# 第 5.3 章：Git 不只是备份——快照、提交边界与可审查协作

**适用版本：** Git 2.x、Python 3.11+  
**项目连接：** `02_可运行项目/projects/05-cli-tool-platform/`

## 1. 本章目标

本章完成后，你能够区分工作区、暂存区和提交；能用 `git status`、`git diff`、`git add`、`git commit`、`git log` 建立可审查的小提交；能正确使用 `.gitignore`；并能解释为什么 Git 历史是生产 Agent 系统中可追溯工程决策的一部分，而不是“把文件传到云端”的同义词。

## 2. 为什么需要版本控制

程序不是一次写完的。你会尝试方案、修复 Bug、升级依赖、改变 API、撤回错误设计。没有版本控制时，“哪个改动导致测试失败”“生产配置是谁改的”“能否恢复上周可用状态”都会变成猜测。Git 让你保存可检验的项目快照，并让改变被解释、审查和回归测试。

## 3. 从生产级 Agent 倒推

一个生产 Agent 的行为可能随着提示词、模型版本、工具 Schema、检索参数、评测集和部署配置改变。若这些改变没有可读提交和对应测试，线上结果就无法复现。Git 不保存运行时全部状态，也不替代审计日志、数据库备份或密钥管理；它负责记录被选择提交到仓库的工程工件及其演进。

## 4. Git 的快照模型

Git 将提交视为项目文件系统在某一时刻的快照，而不是仅保存“上一版到下一版的文本差异”。未改变文件会高效复用；每次提交则创建一个可引用的历史节点。[1] 这个模型帮助你理解：提交不是“自动保存”，而是你主动声明“这些文件一起代表一个有意义、可验证的状态”。

> **提交原则：** 一个提交应表达一个可以说明、检查并最好能独立测试的改变。

## 5. 三个状态与三个区域

| 文件状态 | 所在区域 | 含义 | 常用检查 |
|---|---|---|---|
| 已修改（modified） | 工作区（working tree） | 文件改变了，尚未选择进入下次提交。 | `git diff` |
| 已暂存（staged） | 暂存区（staging area / index） | 当前版本已被选择进入下次提交。 | `git diff --staged` |
| 已提交（committed） | 本地 Git 数据库 | 快照已写入本地历史。 | `git log --oneline` |

Git 官方 Pro Git 书将工作区、暂存区和 Git 目录描述为核心区域，并强调修改、暂存、提交是不同状态。[1]

## 6. 最小安全工作流

在 `02_可运行项目/projects/05-cli-tool-platform/` 项目根目录中执行以下命令。首次初始化只需一次；不要在未知目录中盲目运行 `git add .`。

```bash
cd 02_可运行项目/projects/05-cli-tool-platform
git init
git status --short
git add pyproject.toml README.md src tests .github .gitignore
git diff --staged
git commit -m "feat: add reproducible CLI project skeleton"
git log --oneline --max-count=3
```

`git status --short` 先显示将发生什么；`git add` 明确选择文件；`git diff --staged` 在提交前检查所选内容；提交信息用动词开头并说明意图。请勿把密码、令牌、`.env`、虚拟环境或构建缓存纳入本次提交。

## 7. 逐行解释安全工作流

`git init` 创建本地仓库元数据；它不自动将文件上传到远程服务。`git status` 展示工作区和暂存区差异；它是每次操作前后最重要的“现实检查”。`git add` 选择具体文件版本，而不是“批准整个目录”。`git diff --staged` 显示下一次提交真正包含什么，可发现误加入的调试语句、密钥或大文件。`git commit` 只把暂存区快照写入**本地**历史；还需配置远程并显式 `git push` 才会分享。

## 8. 示例：一次可审查变更

假设你为环境检查 CLI 增加了 `--json` 输出。不要把该功能、格式化全仓库、升级五个依赖、改 README 和删除旧文件混成一个提交。建议按以下顺序工作：先加行为测试，提交测试；实现功能，提交实现和 README；最后如需要独立执行格式化。这样失败、回滚和代码审查都更清晰。

```text
test: define JSON environment output contract
feat: add JSON output to environment check CLI
docs: document JSON output example
```

小提交不等于机械拆碎。若实现和测试必须一起才能通过，它们应在同一提交；拆分标准是“是否能解释、构建和验证”。

## 9. `.gitignore` 的真实含义

`.gitignore` 只告诉 Git 忽略**尚未被跟踪**的匹配文件。它不会自动停止追踪已经提交过的文件；若一个密钥曾被提交，后来加入 `.gitignore` 并不能从历史中移除它。[2] 因此忽略规则是预防生成物和本地文件污染的工具，不是泄露后的补救方案。

```gitignore
# 文件：02_可运行项目/projects/05-cli-tool-platform/.gitignore
.venv/
__pycache__/
.pytest_cache/
.mypy_cache/
.ruff_cache/
*.egg-info/
.env
```

## 10. 忽略规则的验证

不要假定规则生效。使用 `git check-ignore -v` 显示匹配文件和规则来源：

```bash
git check-ignore -v .venv/ .pytest_cache/ src/cli_tool_platform.egg-info/
```

本项目验证过 `.venv/`、测试缓存、mypy/Ruff 缓存、`__pycache__/` 与 `*.egg-info/` 会被忽略；`README.md`、`pyproject.toml`、`src/`、`tests/`、`.github/` 则保持可跟踪。若文件已经被跟踪，使用 `git rm --cached 文件名` 从索引移除后再由 `.gitignore` 防止重新加入；操作前必须确认文件仍在工作区并备份敏感内容。[2]

## 11. 错误案例：把密钥交给 Git

下列做法是错误的：将真实 API key 写进 `.env` 后执行 `git add .`，发现问题后只补一条 `.gitignore`。密钥可能已经存在于本地历史、远程分支、代码审查、克隆和缓存中。正确响应是：立即撤销或轮换密钥，评估暴露范围，按组织流程清理历史与日志；不能把“删除当前文件”误认为泄露已消失。本书后续部署章节会进一步讨论密钥注入与运行时配置。

## 12. 错误案例：把提交当备份策略

Git 本地提交通常只保存在当前机器；硬盘损坏、误删目录或未推送分支仍会造成损失。远程仓库、受控备份、数据库备份、对象存储版本与灾难恢复各有不同职责。提交是可追溯的源码快照，不是对所有数据资产的完整备份策略。

## 13. `git diff` 是提交前的安全门

| 命令 | 比较对象 | 应回答的问题 |
|---|---|---|
| `git diff` | 工作区与暂存区 | 我改了什么但还未选择提交？ |
| `git diff --staged` | 暂存区与最近提交 | 下一次提交确切包含什么？ |
| `git show HEAD` | 最近提交快照 | 上一次提交到底做了什么？ |
| `git status --short` | 三个区域概况 | 当前有哪些未处理变化？ |

在 Agent 项目中，将模型参数、工具权限、评测集或部署清单改动提交前，更要阅读 diff。工具能生成大量改动，人的职责是判断改动是否应进入可信历史。

## 14. 分支是隔离改变，不是隔离安全

分支让你在不改变主线的前提下开发功能、试验重构或修复 Bug。它不自动隔离凭据、文件系统权限、外部 API 调用或数据库副作用。为实验 Agent 工作流创建分支很有价值；但实验代码仍不应默认连接生产数据库或使用生产密钥。

```bash
git switch -c feat/json-environment-output
# 修改、测试、检查 diff、提交
git switch main
```

## 15. 合并前的质量门禁

在请求合并前，至少完成：阅读 `git diff main...HEAD`；执行项目 README 中的安装、pytest、mypy 与 Ruff 命令；确认 `.env`、缓存、构建物未进入暂存区；检查提交信息能解释意图；如改变了用户行为或配置契约，更新文档和测试。CI 会重复机器可执行部分，但不会替你判断业务风险、隐私影响和产品语义。

## 16. Git 与 CI 的关系

CI 通过 Git 提交或拉取请求触发，检出指定快照并运行质量命令。本项目的 `quality.yml` 在 Python 3.11 和 3.12 上执行可编辑安装、pytest、mypy 与 Ruff。CI 证明“某个提交在某个声明环境下通过了这些检查”；它不证明系统已部署、用户价值已验证或依赖绝对安全。

## 17. Traceback 与版本定位

当线上 Traceback 出现时，记录应用版本或 Git 提交 ID 能将错误映射回源代码快照。不要把完整用户输入、密钥或内部路径塞进版本标识。最小诊断集通常包括：服务版本、提交 ID、解释器版本、请求相关 ID、错误类型和安全脱敏后的上下文。后续日志章节将实现这一边界。

## 18. 工程、性能与安全取舍

频繁小提交通常让定位更容易，但过于零碎会增加审查负担。自动格式化可能产生大 diff，应与功能改变分开。二进制大文件、模型权重、生成缓存和运行日志通常不适合直接放入普通源码仓库；需要按团队规定使用制品库、对象存储或专门的数据版本策略。版本控制中的“可见”本身是一种安全暴露面。

## 19. 单元与命令验证

本章的可验证动作不是“看见 Git 图标变绿”，而是：使用 `git check-ignore -v` 验证忽略规则；用 `git diff --staged` 检查暂存内容；执行 CLI 工具平台的 pytest、mypy 与 Ruff；用 `git status --short` 验证生成物未被跟踪。对于演示仓库，可以在临时目录初始化 Git，避免对真实项目历史做教学性破坏。

## 20. 本章验收

为 CLI 工具平台创建一个本地提交：仅提交 README、配置、源码、测试、CI 和 `.gitignore`；证明虚拟环境和缓存未被暂存；运行全部质量命令；将 `git log --oneline -1`、`git status --short`、`git diff --staged` 的输出写入学习记录。若你没有准备远程仓库，不要执行 `git push`；本章不要求发布代码。

## 21. 快速测试（5 题）

1. 用一句话说明**Git 快照、提交边界与可审查协作**要解决的核心问题。
2. 写出本章一个最重要的输入、处理和输出边界。
3. 给出一个最小反例，说明忽略该边界会产生什么错误。
4. 说明本章概念与前一章一个概念如何衔接。
5. 判断一句错误说法并改正：只要程序“能运行”，就已经满足本章的工程要求。

## 22. 代码阅读（2 题）

1. 从本章任一可运行示例选取 8–15 行，标注每个变量/对象/函数的输入、变化和输出；说明其中一行为什么不能随意删除。
2. 阅读对应项目或示例中的一个失败分支，画出“输入 → 验证 → 受控结果”的三步链路；指出它没有记录或打印的敏感信息。

## 23. Debug（2 题）

1. 故意把本章一个合法输入改成边界外输入，先记录 Traceback 或受控错误的最后一行，再定位最靠近自己代码的失败点并修复。
2. 制造一个看似能运行、但违反 **Git 快照、提交边界与可审查协作** 合同的小错误；写出复现步骤、预期/实际结果、根因和最小回归测试。

## 24. 编程练习（3 题）

1. 将本章一个重复步骤重写为最小可运行函数或模块，明确参数、返回值和异常/错误边界。
2. 为该实现写至少两个测试：一个正常路径、一个边界或失败路径；断言可观察结果而不是内部实现细节。
3. 增加一个不泄露正文或敏感数据的最小诊断摘要，并验证用户结果与诊断输出职责分离。

## 25. 逆向设计与课后项目

**逆向设计：** 假设一个初学者项目在 **Git 快照、提交边界与可审查协作** 上失败：输入不可复现、状态不清、错误无法定位、数据被静默覆盖或结果难以验证。倒推至少五项缺失的规则、测试、日志、命名或操作边界，并按“先阻止什么风险”排序。

**课后项目：** 在本章已有示例基础上完成一个小型、可运行、可测试的改造。项目必须写明目标、输入、输出、失败案例、运行命令、两个自动化测试和一个逆向设计结论；不得读取真实秘密、执行未经授权的网络/文件副作用，或把用户正文写入日志。
